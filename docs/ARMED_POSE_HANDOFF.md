## 0. 왜 armed pose인가

`coord_to_goal_node`는 토마토 **1개마다** look pose로 복귀한다. 그런데 복귀 이유가
코드 주석상 순전히 **인식**이다:

> `RETURN_TO_LOOK_POSE_DELAY_SEC` 주석 — "팔이 목표 지점에 계속 머물면 카메라가 다음
> 토마토를 넓게 못 보고, 방금 접근한 토마토조차 화면 가장자리에 bbox가 걸려 depth가
> 무효해짐"

기구학적 이유가 아니다. 그리고 이 팔은 look-then-move라 **관측은 시퀀스당 1회면
충분하다** — `harvest_sequence_node`가 스냅샷 시점에 한 번만 TF를 조회해 큐 전체를
`g_base`로 변환하므로(그 파일 L115-144), 2번째 토마토부터는 팔이 어디에 있든 목표
좌표가 흔들리지 않는다. `coord_to_goal_node`도 `frame_id == g_base`면 TF를 아예 안
탄다(L1216-1221).

즉 **look pose(관측)와 대기 자세를 분리할 수 있다.** look pose의 J1은 −7.5°인데 실측
토마토 15개가 정렬에 요구하는 J1은 +10~+49°에 몰려 있어, 매 사이클 그 간격을 왕복해
왔다.

`[시각화 제안]` **사이클 구조 전후 대비도**. 위: `look → target → look → target → …`
(look pose가 매번 끼어듦). 아래: `look → armed → target → armed → target → … → look`.
look pose 아이콘에 카메라를, armed pose 아이콘에 시계(대기)를 붙이면 역할 차이가 보인다.

## 1. 어떻게 정했나 — 1차 실패와 2차 도출

### 1.1 폐기된 1차 시도 — 관절공간 중심

15개 목표의 **정렬 관절해**를 모아(`scripts/sweep_targets_planned.py
--collect-solutions`) 관절공간 minimax 중심을 좌표하강으로 구했다
(`scripts/find_armed_pose.py`). 결과:

```
(+27.08, -2.39, -63.53, +1.70, -80.44, +64.83)도
```

**사용자가 RViz에서 "베드에 너무 가깝다"고 발견했고, FK로 확인하니 사실이었다:**

| | flange | 반경 | 방위 | 가장 가까운 토마토까지 |
|---|---|---|---|---|
| 1차 armed pose | (+0.194, −0.024, +0.306) | 0.195 m | **−7°** | **7.3 cm** |
| look pose | (−0.136, −0.035, +0.241) | 0.141 m | −166° | 38.9 cm |

그리퍼가 flange에서 9 cm 더 나가므로 **손가락은 이미 열매 사이**에 있는 자세다.

**원인 둘.**
1. **목적함수.** "모든 목표까지 관절 이동량 최소"는 제약이 없으면 **목표 한가운데로
   파고드는 것**이 최적해다. 당연한 결과였는데 예상하지 못했다.
2. **작업공간을 확인하지 않았다.** 관절공간의 중심이 작업공간에서 안전하다는 보장이
   전혀 없다. FK를 한 번만 돌려봤으면 즉시 드러났다.

> **교훈: 관절공간에서 자세를 만들었으면 반드시 FK로 작업공간 위치를 확인할 것.**

### 1.2 채택된 2차 도출 — 작업공간 안전 조건 먼저

`scripts/find_armed_pose_cartesian.py`.

1. 토마토 15개를 **구 collision object**로 씬에 넣는다(검출 반지름 + 1 cm 여유)
2. **ACM**으로 그리퍼/손목/flange만 토마토 충돌을 허용한다 (2.2절 — 이게 없으면 성공률 2~4%)
3. **작업공간 안전 조건**으로 후보를 거른다: 그리퍼 **끝단**이 어느 토마토에서든 8 cm 이상
4. 살아남은 후보에서 15개 목표로 플래닝해 성공률·이동량을 잰다

#### 여기서 드러난 구조적 사실

처음엔 후보를 "flange를 반경 r·방위 az·높이 h에 놓고 **그리퍼가 베드를 향하게**"
만들었다. **36개 중 34개가 여유 부족으로 탈락하고 나머지 2개도 도달 불가였다.**

이유가 구조적이다 — 그리퍼가 베드를 향하면 끝단이 **반경 + 9 cm**가 되어 토마토
(반경 0.248~0.293)에 닿는다.

look pose가 왜 안전한지 보면 답이 나온다. **flange 방위각이 −165.7°**, 즉 팔이
**베이스 뒤로 접혀** 있고 카메라만 앞을 본다.

> **안전한 대기 자세는 "뻗은" 자세가 아니라 "접힌" 자세다.**

그래서 후보를 *look pose의 접힌 기하를 유지한 채 J1(+J2/J3)만 바꾼* 족으로 다시
만들었다. 안전은 접힌 기하가 보장하고, 이득은 J1 회전이 만든다. 21개 후보 전부가
끝단 여유 **24~32 cm**로 통과했다.

`[시각화 제안]` **"뻗은 vs 접힌" 평면도 2장.** 왼쪽: 그리퍼가 베드를 향한 자세 —
끝단이 열매 사이에 박히는 그림에 7.3 cm 화살표. 오른쪽: 뒤로 접힌 자세 — 33 cm 화살표.
같은 flange 반경(0.14~0.19)인데 여유가 4.6배 차이라는 게 메시지다.

### 1.3 채택값

```python
ARMED_POSE_JOINT_POSITIONS = [+40.00, +104.06, -56.68, -50.00, +15.99, +1.40]  # 도
# = look pose에서 J1만 +40도 돌린 것. J2~J6는 look pose와 동일.
```

| 항목 | 값 |
|---|---|
| flange | (−0.067, −0.124, +0.241), 반경 0.141 m, 방위 −118° |
| 가장 가까운 토마토까지 | **33.3 cm** (1차 7.3 cm, look pose 38.9 cm) |
| 플래닝 성공률 | 15/15 목표 **100%** |
| 이동량 | 중앙 502°, 최악 566° |

**J2~J6는 손댈 이유가 없었다.** 21개 후보를 전부 평가한 결과가 "J1만 돌려라"였다.

### 1.4 타겟별 armed pose (옵션2) — 측정만 하고 미채택

`docs/new_concept.md` 옵션2. 같은 21개 후보 중 목표마다 최적을 고르면:

| | 이동량 중앙 | 최악 |
|---|---|---|
| 단일 armed pose | 502° | 566° |
| **타겟별** | **399° (−20.6%)** | **506° (−10.7%)** |

**서로 다른 자세가 9개** 필요하다(J1이 0°~60°에 흩어짐, 각 토마토의 방위각을 따라감).
15개 목표에 9개 자세면 "대기 자세"라는 개념이 사실상 없어지고 구조가 복잡해져,
우선 단일 자세를 채택했다.

> **[2026-08-02 정정] 위 표는 `armed → 목표` 편도만 잰 값이다.**
> 타겟별 armed pose의 이득은 편도가 아니라 **`목표ᵢ → armed_{i+1}` 전이**에
> 있는데 그게 빠져 있다. 즉 이 −20.6%는 이 선택지를 평가하는 수치가 아니다.
> 사슬로 다시 잰 결과는 1.5절에 있다.
>
> 또 *"데이터는 남아 있다"*도 절반만 맞다. `bags/armed_pose_v2.json`에는 요약
> 통계 3개만 있고 **목표→자세 매핑과 9개 관절벡터는 저장되지 않았다**
> (`find_armed_pose_cartesian.py`가 `len(chosen)`만 직렬화한다).

### 1.5 타겟별 armed pose 재검토 — 사슬로 다시 쟀다 (2026-08-02)

1.4절의 기각이 지금도 유효한지 사용자가 재검토를 요청했다. 요지는:

> 지금은 모든 목표가 하나의 armed pose에서 출발하고 수확 때마다 그리로 돌아온다.
> 사람이라면 토마토 하나 따고 집에 갔다 다시 나오지 않는다. i번째 armed pose는
> i번째 목표를 위한 것이고, 1번을 딴 뒤엔 2번에 접근하기 좋은 자세로 가야 한다.

맞는 지적이고, **그 이득을 잰 측정이 그때도 지금도 없었다.** 그래서 새로 만들었다
(`scripts/eval_armed_chain.py`). 접근·파지·후퇴는 어느 방식이나 같으므로
**전이(transit)만** 재고, 15개 목표를 순서대로 도는 **사슬 전체**를 합산한다.

| 방식 | 경로 |
|---|---|
| **A** 현재(단일) | `look → armed → [tᵢ] → armed → … → armed → look` |
| **B1** 타겟별(규칙) | `look → armed₁ → [tᵢ] → armed_{i+1} → … → look`, armedᵢ의 J1을 목표 정렬 J1에 맞춤 |
| **B2** 타겟별(그리디) | 같은 구조, armedᵢ를 후보 4개 중 전이 합 최소로 선택 |
| **C** armed 없음 | `look → [t₁] → [t₂] → … → look` (정렬에서 정렬로 직행) |

씬은 열매+octomap+벽, **octomap ACM 완화 ON**, 반복 3회(구간별 최소).

| 방식 | 통 없음 | 통 포함 |
|---|---|---|
| A 현재(단일) | 12934° | 16077° |
| B1 타겟별(규칙) | 12740° (**−1.5%**) | 15389° (**−4.3%**) |
| B2 타겟별(그리디) | 12926° (**−0.1%**) | 15861° (**−1.3%**) |
| **C armed 없음** | **6315° (−51.2%)** | **11241° (−30.1%)** |

#### 결론 1 — 타겟별은 채택할 이유가 없다. 1.4절의 기각이 옳았다

**B2가 결정적이다.** 후보 4개(J1 −20/0/+20/+40) 중 자유롭게 고르게 했더니
통 없이는 **15개 전부 +40°**(서로 다른 자세 **1개**), 통을 넣어도 14개가 +40°
(자세 **2개**)였다. **최적화기가 자유롭게 고를 수 있는데도 단일 armed pose로
수렴한다.** 편도로는 −20.6%로 보이던 것이 사슬로는 −1.5%다.

곁들여 정리된 것 둘:

- **벽이 armed 족을 J1 ≤ +50에서 자른다.** +60/+70은 joint4가 벽에 걸린다.
  1.4절이 전제한 "J1 0~60°에 흩어진 9개 자세"는 **더 이상 성립하지 않는다.**
- **안전은 기각 사유가 아니었다.** 족 전체의 그리퍼 끝단 여유가 26~30cm로
  단일 armed pose(33.3cm)보다 조금 작을 뿐 8cm 기준을 크게 넘는다.

#### 결론 2 — 줄일 여지는 armed pose **자체**에 있다

C가 통 없이 **−51%**, 통 포함 **−30%**다. 사용자의 사람 비유가 맞았는데, 답이
"목표마다 다른 집"이 아니라 **"집에 아예 안 가는 것"**이었다.

이유는 기하다. armed pose는 팔을 **뒤로 접은** 자세(flange가 베이스 뒤 x=−0.067)
이고 정렬 위치는 베드 앞(반경 0.13~0.175)이다. 목표에서 목표로 가는데 매번 뒤로
접었다 펴는 셈이라 **경유가 지름길이 아니라 우회**다. armed pose가 이득인 것은
**look pose에서 첫 목표로 갈 때뿐**이다.

> 그래서 `A'(현재 + 복귀만 삭제)`는 따로 잴 필요가 없었다 — 단일 자세에서는
> 복귀를 없애도 `[0/5]`가 결국 같은 자세를 경유하므로 A와 경로가 같아진다.
> **"복귀 삭제"는 armed pose가 목표마다 다를 때만 내용이 생긴다.**

#### 곁가지 — armed pose의 J1은 look pose가 아니라 **목표**가 정한다

*"팔이 뒤로 접혀 있어 오른쪽에서 출발하니 armed pose도 오른쪽(+40°)인가,
look pose J1이 −90°였다면 armed pose도 달라지나"* 라는 질문이 나와 직접 쟀다.

기하는 이렇다. look pose는 J2 +104°, J3 −57°로 **팔을 뒤로 접은** 자세라 flange가
베이스 뒤(x=−0.136, 방위각 −166°)에 있고 카메라만 앞을 본다. J1을 +로 돌리면
flange 방위각이 따라 올라가 −118°(armed, +40°)로 **오른쪽·뒤**로 간다. 반면 목표는
앞(방위각 −14~+20°)이고 정렬에 필요한 J1은 **+10~+62°**다. 즉 armed pose는
**Cartesian으로는 오른쪽 뒤인데 관절공간으로는 목표 쪽으로 미리 가 있는** 자세다.

| | J1 |
|---|---|
| look pose | −7.5° |
| **목표 정렬 J1 중앙값** | **+42.0°** |
| 현재 armed pose | +40.0° |

사슬 A 비용을 armed J1의 함수로 재면(벽 없음, ACM 완화 ON, 반복 2회):

| armed J1 | −20 | 0 | +20 | +40 | **+60** | +70 |
|---|---|---|---|---|---|---|
| 사슬 A 비용 | 13303° | 12661° | 12149° | 11708° | **11510°** | 11559° |

**look pose(−7.5°)에서 멀어질수록 단조 감소하다 +60° 근처에서 최소**다.
즉 **armed pose의 J1은 look pose와 무관하고 목표 분포가 정한다.**

그래서 look pose J1을 바꿔도 armed pose 족(look pose의 J2~J6 유지 + J1 변경)은
그대로이고 최적 J1도 목표가 정한다. **다만 간접적으로는 크게 달라진다** —
look pose를 옮기면 `APPROACH_REFERENCE_POINT`(그 자세의 FK)가 따라 움직여
**목표별 정렬 자세가 통째로 바뀌고**, 그러면 정렬 J1 분포도 최적 armed J1도 바뀐다.
`WORLD_UP`(6.2절)과 카메라 프레이밍도 같이 걸린다.

> **J1 위에 독립된 제약이 둘 얹혀 있다.** look pose J1은 *카메라가 베드를 보는가*가
> 정하고, armed pose J1은 *목표들이 어디 있는가*가 정한다. 지금 −7.5°와 +40°가
> 47.5° 떨어져 있는 것은 두 제약이 서로 다른 답을 냈기 때문이지 하나가 다른 하나에서
> 파생된 것이 아니다.

부수적으로 **현재 +40°는 최적이 아니다** — +60°가 −1.7% 낫다. 다만 벽이 있으면
+60°는 joint4가 걸려 못 쓰고(J1 ≤ +50), −1.7%는 아래 C의 −51%에 비하면 작다.
`find_armed_pose_cartesian.py`가 +40°를 고른 기준은 "최악 이동량 최소"였고
이번은 "사슬 합 최소"라 기준 자체가 다르다.

#### 벽을 없애도 결론은 안 바뀐다

*"벽이 J1을 +50에서 자르니 타겟별이 손해 본 것 아닌가"* 라는 반론을 막기 위해
벽 없는 octomap으로 같은 사슬을 다시 쟀다.

| 방식 | 벽 있음 | 벽 없음 | 벽 없음(B2 후보 +60 포함) |
|---|---|---|---|
| A 현재(단일) | 12934° | 12203° | 12354° |
| B1 타겟별(규칙) | −1.5% | −1.6% | −2.0% |
| B2 타겟별(그리디) | −0.1% | −0.2% | −1.6% |
| C armed 없음 | −51.2% | −45.1% | −51.6% |

벽을 없애면 **J1 −20~+70 전 구간이 유효**해지고(벽이 유일한 제약이었다) B2가 실제로
+60°를 6개 목표에 쓰지만, 이득은 −1.6%에 그친다. **벽이 타겟별을 막고 있던 것이
아니다.** 벽 자체의 비용은 약 5%(12934 → 12203°)로, 팔의 작업 영역 밖이라는
6.1절 관측과 일치한다.

왜 선택지를 넓혀도 소용이 없는지는 기하로 설명된다 — armed pose 족은 전부 팔을
**뒤로 접은** 자세이고 정렬 위치는 **베드 앞**이다. J1을 어디로 돌리든 **접었다 펴는
왕복 자체**가 비용이고, J1을 미리 돌려둬도 그 왕복은 그대로 남는다.

> **armed pose의 문제는 "어디에 두느냐"가 아니라 "거기에 들르느냐"다.**
> 위치를 최적으로 골라도 −2%, 안 들르면 −51%.

#### 결론 3 — 답은 "통을 대기 자세로 쓰는 것"이다 (D)

사용자 제안: *"지금은 파지 후 토마토를 쥔 채 armed pose로 돌아가는데, 거기에
수확통을 놓으면 어떤가?"*

**문자 그대로는 자리가 안 난다** — armed pose의 그리퍼 끝단이
(−0.017, −0.050, 0.237)로 **베이스 바로 위**이고 그 뒤는 벽(y=−0.20)이다.
하지만 발상을 뒤집으면 된다: **통을 armed pose로 옮기는 대신 armed pose를 통
자리로 옮긴다.** 대기 자세와 놓는 자세를 하나로 만드는 것이다.

    look → 통자세 → [t₁] → 통자세(놓고 대기) → [t₂] → … → look

| 방식 | 전이 합 | 대비 |
|---|---|---|
| A 현재 armed 대기 + 통 별도 | 16077° | — |
| C armed 없음 + 통 | 11241° | −30.1% |
| **D 통 자세 = 대기 자세** | **11165°** | **−30.6%** |

**D가 C만큼 좋은 것은 당연하다** — C에서도 팔은 `정렬ᵢ → 통 → 정렬ᵢ₊₁`을 한다.
D와 경로가 같다. 즉 **통이 이미 대기 자세 역할을 하고 있었고**, A는 거기에
armed pose를 하나 더 끼워 넣은 것이었다. A만 +44% 비싼 이유가 그것이다.

**그리고 D는 C의 대가를 치르지 않는다:**

| 대기 자세 | 열매까지 여유 |
|---|---|
| 현재 armed pose | 33.3 cm |
| **통 자세 (D)** | **27.7 cm** |
| 정렬 위치 (C) | **3 cm** |

C의 −30%는 수확 사이 그리퍼가 열매 3cm 옆에 머무는 것을 대가로 하는데,
**D는 armed pose와 거의 같은 여유를 유지하면서 같은 이득을 얻는다.** 통 자세는
flange (−0.004, +0.161, 0.210), J1 +116.5°로 베드 반대편이기 때문이다.

> **그래서 "armed pose 제거"와 "수확통 편입"은 별개의 일이 아니라 같은 일이다.**
> 통을 사이클에 넣으면 armed pose는 자동으로 필요 없어진다. `[0/5]` 경유 단계도
> 사라지고, 첫 목표만 `look → 통 → 정렬₁`로 시작하면 된다.

채택 전 확인할 것: 반복 10회 이상으로 재확인, 순서 의존성(C·D는 순서가 곧
비용인데 현재 순서는 카메라 깊이순), 좌우 비대칭(아래), 그리고 **놓은 직후 그
위에 2.7초 머무는 것이 실물에서 괜찮은지**(열매가 튀거나 다음 열매와 겹치는 문제).

#### 곁가지 — 통이 왼쪽이냐 오른쪽이냐로 17% 갈린다

두 대의 동일한 코봇이 나란히 서서 각자 앞의 베드를 보고, 통이 그 사이에 있는
배치를 가정하면 **한 대는 통이 왼쪽(+Y), 다른 한 대는 오른쪽(−Y)**이 된다.
같은 기계·같은 자세인데 결과가 다르다(벽 없음, ACM 완화 ON, 반복 5회):

| | 통이 왼쪽(+Y) | 통이 오른쪽(−Y) |
|---|---|---|
| 통 자세 J1 | +115.5° | −59.1° |
| 파지 → 통 → armed (중앙) | **613°** | **717° (+17%)** |
| 성공률 | 15/15 | 15/15 |

원인은 **손목의 73.2 mm 측면 오프셋**(`joint6_to_joint5` origin (0, −0.07318, 0))
이다. 거울상이라면 J1이 부호만 다른 같은 크기여야 하는데 **+115.5° vs −59.1°로
크기 자체가 두 배 가까이 다르다.**

목표 정렬 J1이 **전부 양수**(+10~+62°)라, 통이 그 연장선(왼쪽)에 있으면 가던
방향으로 이어지고 반대쪽이면 되돌아와야 한다. `armed → 통`만 보면 오히려 오른쪽이
싸지만(268 vs 282°), **실제 사이클에서 통으로 가는 것은 파지 직후**라 그쪽이 중요하다.

> **4절이 통 위치를 y=+0.15로 확정한 것은 결과적으로 유리한 쪽이었다.**
> 좌우 임의 선택이 아니었다는 근거가 여기서 처음 생긴다.

두 대를 운용한다면 선택지는 (a) 통을 각 코봇 왼쪽에 하나씩, (b) 통 하나를 두
코봇의 **같은 쪽**에 두어 거리 손해와 방향 이득을 맞바꾸기, (c) 불리한 쪽만
armed/통 자세를 따로 튜닝, (d) +17%를 감수. (b)와 (c)는 지금 도구로 바로 잴 수 있다.

#### C의 대가, 그리고 수확통과의 관계

C는 수확 사이 팔이 베드 안에 머문다. 정렬 위치의 그리퍼 끝단은 **열매에서 3cm**다
(armed pose는 26~33cm). 그 상태로 다음 목표를 기다리는 시간이 사이클당 2.7초
(`OCTOMAP_CLEAR_DELAY_SEC` 1.2 + `NEXT_TARGET_DELAY_SEC` 1.5)다.

**그런데 수확통을 사이클에 넣으면 이 대가가 상당 부분 사라진다.** 파지 직후 통
(J1 +105°)으로 가면 베드를 빠져나오므로, 대기가 열매 옆이 아니라 통 위에서
일어난다. **즉 통 편입과 armed pose 제거는 같이 결정해야 한다** — 통이 armed
pose의 안전 역할을 대신한다.

통 자체의 비용도 크다. A 기준 12934 → 16077°(+24%), C 기준 6315 → 11241°(+78%).
C에서 증가폭이 큰 것은, A는 이미 armed(+40°)를 경유하느라 J1을 크게 돌고 있어
통(+105°)까지의 추가분이 상대적으로 작은 반면 C는 순수 추가이기 때문이다.

**유효 범위**: 반복 3회(구간별 최소라 낙관 편향), 순서는 검출 파일 순서 —
실물은 카메라 깊이 z 오름차순이라 다르다(`harvest_sequence_node.py:149`).
단일 armed pose에서는 목표 간 비용이 대칭이라 순서가 공짜였지만 C·B에서는
순서가 곧 비용이므로, **채택 전에 실제 순서로 재확인할 것.**
원자료 `bags/armed_chain_acm.csv`(통 없음), `bags/armed_chain_bin.csv`(통 포함).

`[시각화 제안]` **사슬 막대 4개**(A/B1/B2/C)를 통 없음·통 포함 두 계열로.
C만 뚝 떨어지고 B가 A에 붙어 있는 그림이 결론 두 개를 한 번에 보여준다.
옆에 **B2가 고른 J1 목록**(전부 +40°)을 작게 붙이면 "최적화기가 단일로 수렴"이
직관적이다.

## 2. 측정 함정 — 이 문서에서 가장 중요한 절

이 작업에서 낸 수치의 절반 이상이 한 번씩 폐기됐다. 원인이 전부 측정 환경이었다.
**새 수치를 낼 때마다 이 목록을 확인할 것.**

### 함정 1 — `move_group`이 2개 뜨면 조용히 섞인다

`enable_octomap:=false`로 띄운 스택인데 로그에 `<octomap>` 충돌이 655건 찍혔다.
그때 `move_group`이 2개였고, 하나가 재생된 토마토 베드로 octomap을 채우고 있었다.

```bash
ps -eo comm | grep -c '^move_group$'   # 반드시 1이어야 한다
```

**프로세스명이 15자로 잘린다는 점에 주의.** `pkill -x coord_to_goal_no`는 실제
프로세스명(`coord_to_goal_n`)과 안 맞아 조용히 실패한다. `pkill -f` 경로 매칭이 안전하다.

### 함정 2 — `enable_octomap:=false`가 실제로는 안 먹는다 (미해결 버그)

`move_group` 1개만 띄우고 `enable_octomap:=false`를 줬는데도:

```bash
ros2 param get /move_group sensors     # -> ['d435_pointcloud']
```

`docs/SPEED_TUNING_HANDOFF.md` 11절에 같은 관측이 미해결로 기록돼 있었고 재현됐다.
**런치 인자 전달 경로 자체의 버그다.** 클라우드 발행자가 없으면 octomap이 0바이트라
무해하지만, **함정 1의 통로가 된 것이 이 버그다.**

octomap이 실제로 비어 있는지는 이렇게 확인한다:

```bash
ros2 service call /get_planning_scene moveit_msgs/srv/GetPlanningScene \
  "{components: {components: 2}}"      # octomap.data가 0바이트여야 한다
```

### 함정 3 — collision object 없이 재면 "뚫고 가는 경로"가 성공으로 잡힌다

가장 크게 데인 함정이다. 세 번 반복됐다:

| 대상 | 증상 | 발견 시점 |
|---|---|---|
| 수확통 | 이동량 288° → 실제 379° (32% 낙관) | 통을 씬에 넣고 재측정 |
| 토마토 | 편도 452° → 실제 502° | armed pose 재도출 중 |
| 베드 줄기·지지대 | **성공률 100% → 77.8%** | 5절 (octomap 재검증) |

세 번 다 같은 모양이다 — **없던 장애물을 넣을 때마다 수치가 나빠졌고, 한 번도
좋아진 적이 없다.** 그런데 세 번째가 앞의 둘과 다른 점이 하나 있다:
앞의 둘은 이동량이 30% 나빠졌고, 세 번째는 **이동량은 7% 나빠졌는데 성공률이
22%p 떨어졌다.** 넣은 장애물의 종류에 따라 **어느 지표가 망가지는지가 다르다** —
그래서 이동량만 보고 있으면 세 번째 같은 것을 통째로 놓친다.

`[시각화 제안]` 앞의 두 줄은 "같은 경로, 장애물 유무에 따라 288 vs 379" 대비도가
좋고, 세 번째 줄은 **이동량 막대는 거의 같은데 성공률 막대만 뚝 떨어지는** 그림이
좋다 — "무엇을 재고 있었나"가 메시지다.

### 함정 4 — 토마토를 씬에 넣으면 ACM이 **필수**다

토마토를 collision object로 넣자 성공률이 **2~4%**로 떨어졌다. 접근할 토마토
**자신과** 충돌하기 때문이다.

`coord_to_goal_node`는 이미 같은 처리를 한다(`_allow_gripper_target_object_collision`,
L1352) — 그 함수 주석에 *"그 자리에 등록된 구가 flange 자신과 충돌로 잡혀서 Unable to
sample any valid states for goal tree로 매번 실패"* 라는 실측 기록이 있고, joint5/joint6도
같은 이유로 허용 목록에 있다.

허용 대상: `GRIPPER_LINK_NAMES + WRIST_LINK_NAMES + [END_EFFECTOR_NAME]` = 10개 링크.
**팔뚝(joint2~4)은 허용하지 않는다** — 팔이 베드를 관통하는 경로는 그대로 걸러야 한다.

> **ACM diff는 병합이 아니라 통째 대체다.** 부분 발행하면 SRDF의
> self-collision-disable이 전부 소실된다(`docs/obstacle_avoidance_manual_test.md`의
> 실제 사고). 반드시 **조회 → 보존 → 추가 → 재발행**.

### 함정 5 — 스윕 스크립트가 노드 로직을 재현하지 않는다

`scripts/sweep_targets_planned.py`의 `select_approach()`는 elevation_error 최소 후보
1개를 **roll=0으로** 고를 뿐, 노드의 고도각 25개 × roll 12개 `compute_ik` 격자 랭킹을
돌리지 않는다. 기본 허용오차도 0.05 rad인데 **노드는 0.2**다(L1898).

즉 이 스크립트로 잰 값은 "노드가 이 토마토를 딸 수 있는가"가 아니라 **"이 좌표에 pose
goal로 갈 수 있는가"**다. 노드 비교에는 `--orientation-tolerance 0.2`를 반드시 줄 것.

### 함정 6 — 반복 10회로는 IK 분기 무작위성에 묻힌다

같은 목표·같은 시작 자세인데 J1 도달각이 시도마다 갈린다. 반복 10회(점당 75시도)에서는
순위가 뒤집혔고, 30회로 올려야 안정됐다. **이동량은 이봉분포이므로 평균이 아니라
중앙값·IQR로 볼 것.**

### 함정 7 — 출력 버퍼링

후보 수십 개 × 목표 15개는 수십 분이 걸린다. 파이프로 넘기면 블록 버퍼링돼 **1시간 동안
아무것도 안 보인다**(실제로 겪고 중단시켰다). `python3 -u` 또는 `print(flush=True)`.

### 함정 8 — 씬의 시작 상태를 가정하면 안 된다

`eval_bed_scene.py`를 처음 돌렸을 때 `empty` 조합이 **octomap voxel 988개짜리**
였다. 앞선 `octomap_io.py inject` 테스트가 남긴 것을 그대로 물려받은 것이다.
스크립트는 "아직 아무것도 안 넣었으니 비어 있겠지"라고 시작 상태를 가정했다.

씬은 **move_group 프로세스에 붙어 있고 스크립트보다 오래 산다.** 그래서 조합마다
되읽어 확인하게 고쳤고(`verify_scene`), 그 검증이 첫 실행에서 바로 걸렸다.

> **함정 3의 재발 경로가 이것이다.** 3은 "장애물을 안 넣어서" 낙관했고,
> 8은 "안 넣은 줄 알았는데 들어 있어서" 반대로 비관한다. 둘 다 원인은 하나 —
> 씬을 확인하지 않은 것.

빈 octomap을 `PlanningScene` diff로 발행하는 방법으로는 **안 지워진다.**
`setPlanningSceneDiffMsg`가
`if (!world.collision_objects.empty() || !world.octomap.octomap.data.empty())`로
걸러서, data가 비면 world 처리를 아예 호출하지 않는다. `/clear_octomap`을 쓸 것.

### 함정 9 — 반복 3회로는 "도달 불가"를 오판한다

함정 6(반복 10회로는 분기 순위가 뒤집힌다)의 확장인데, 이쪽이 더 나쁘다.
같은 씬·같은 시작 자세인데 **전회 실패로 잡히는 목표 개수가 반복 수에 따라 달라진다:**

| 반복 | full 씬 / armed pose | 도달 불가 판정 |
|---|---|---|
| 3회 | 성공률 68.9% | **2개** |
| 30회 | 성공률 76.7% | **1개** |

3회짜리로 "이 토마토는 못 딴다"고 쓰면 절반이 틀린 말이 된다. **도달 가능성은
이동량보다 더 많은 반복을 요구한다** — 이동량은 성공한 시도의 분포지만,
도달 가능성은 "한 번이라도 성공했는가"라 꼬리를 봐야 하기 때문이다.

### 함정 10 — 세션이 다르면 같은 씬도 ±8% 다르다

`tomato` 씬 / armed pose를 서로 다른 스택 세션에서 두 번 쟀다(둘 다 반복 30회,
같은 스크립트·같은 목표·같은 씬):

| | look pose | armed pose |
|---|---|---|
| 1차 세션 | 490° | 406° |
| 2차 세션 | 453° | 432° |
| 차이 | −7.6% | **+6.4%** |

**즉 한 자릿수 % 차이는 조건의 효과가 아니라 잡음이다.** 앞선 측정들이 스택을
새로 띄우며 조건을 바꿔 왔다는 점을 생각하면, 문서 곳곳의 "−9%" 같은 수치는
이 폭 안에 있다.

그래서 `eval_bed_scene.py`는 **한 프로세스 안에서 씬만 갈아 끼운다.** 조건 비교는
반드시 한 세션 안에서 할 것 — 다른 세션의 수치와 빼기를 하면 안 된다.

### 함정 11 — bbox padding을 낮추면 **열매가 octomap으로 들어와** ACM을 우회한다

가장 크게 데인 함정이고, 하마터면 반대 결론을 쓸 뻔했다.

`docs/ROSBAG_HANDOFF.md` 6.5절이 `bbox_padding_ratio = 0.5`가 과하다고
기록해 뒀다 — 토마토뿐 아니라 **줄기·지지대까지 octomap에서 지워진다**는 것이다.
그래서 "0.2로 낮추면 줄기가 더 남으니 더 보수적인(=실물에 가까운) 씬이 되겠다"고
보고 0.2짜리 octomap을 하나 더 만들어 쟀다. 결과가 극적이었다:

| padding | 성공률(full/look) | 도달 목표 |
|---|---|---|
| 0.5 (현재값) | 77.8% | 14/15 |
| **0.2** | **19.3%** | **5/15** |

**그런데 이건 줄기 때문이 아니다.** 토마토 중심에서의 거리로 voxel을 나눠 보면:

| padding | 열매 구 **안** | 껍질 밖 1~3cm | 3~5cm |
|---|---|---|---|
| 0.5 | **0개** | 140개 | 242개 |
| 0.2 | **33개** (13/15 토마토) | 316개 | 384개 |

padding 0.2에서는 bbox가 열매를 다 덮지 못해 **열매 표면 포인트가 살아남아
octomap voxel이 된다.** 그리고 **octomap voxel에는 ACM 완화가 안 걸린다**
(함정 4의 ACM은 `tomato_*` collision object에만 붙는다). 즉 따려는 열매 자신이
회피 대상이 되어 접근이 원천 차단된다 — 함정 4와 똑같은 실패인데, ACM으로
막을 수 없는 경로로 들어온 것이다.

> **19.3%는 실물이 더 어렵다는 뜻이 아니라 측정이 망가졌다는 뜻이다.**
> "파라미터를 보수적으로 잡았더니 나빠졌다"를 "실물이 그만큼 나쁘다"로 읽으면
> 안 된다.

그래서 진짜 결론은 **두 padding 값 어느 쪽도 옳지 않다**는 것이다.
0.5는 줄기를 지워서 낙관적이고, 0.2는 열매를 남겨서 인공적으로 비관적이다.
필요한 것은 "열매는 확실히 지우고 줄기는 남기는" 마스킹인데, 지금의 사각형 bbox
+ 등방 padding으로는 그 둘을 분리할 수 없다(6절 남은 일 2번).

---

아래 넷은 **6절(RViz 스윕 관찰 후속)과 1.5절에서 새로 밟은 것**이다.

### 함정 12 — "게이트 통과 수"만 보고 판단하면 반대 결론이 나온다

사용자가 *"목표 50 mm 앞에서 직진"*을 요청해 `APPROACH_STANDOFF_M`을 50 mm로 올려도
되는지 쟀다. 기하 게이트가 **15/15 통과**여서 "공짜"라고 보고했는데 **틀렸다.**

통과 여부만 봤지 **무엇이 채택되는지를 안 봤다.** 50 mm에서는 완만한 고도각이
`MIN_ALIGN_RADIUS_M`에 걸려 사라지고 탐색이 **더 급한 고도각으로 도망간다**:

| standoff | 통과 | 채택 고도각 | 수직 우회 |
|---|---|---|---|
| 20 mm | 15/15 | −10~+15° | 17 mm |
| 30 mm | 15/15 | −10~+15° | 18 mm |
| 40 mm | 15/15 | −25~+20° | 28 mm |
| 50 mm | 15/15 | **−35~+30°** | **47 mm** |

네 줄 다 "15/15 통과"인데 마지막은 **정면 진입을 위해 늘린 값이 접근을 가장
비스듬하게 만든다.** 요청의 목적과 정반대다.

> **탐색이 실패하지 않고 "다른 답으로 도망가는" 종류의 제약은, 통과/실패가 아니라
> 채택된 값을 봐야 한다.** 게이트는 실패를 안 만들고 선택을 바꾼다.

### 함정 13 — 비동기 `/clear_octomap`이 뒤이은 주입을 덮어쓴다

손으로 인코딩한 octomap을 주입했더니 되읽기가 0바이트라 **"move_group이 우리
형식을 거부한다"고 오진**했다. 실제로는 직전 스크립트가 종료하며 부른
`/clear_octomap`이 **비동기라 우리 주입 뒤에 도착**한 것이었다. 같은 파일을 다시
주입하니 그대로 들어갔다.

`octomap_io.py inject`에 재시도를 넣어 두었다. 스크립트를 연달아 돌릴 때
**앞 스크립트의 정리 작업이 아직 날아가는 중**일 수 있다는 것을 기억할 것.

### 함정 14 — RViz 텍스트 마커는 `2 × scale.z`로 그려진다

상태 라벨이 "월드를 가로질러 흩어진다"는 지적을 세 번 받는 동안 줄 간격·위치·
한글 여부를 고쳤는데 전부 원인이 아니었다. 진짜 원인 둘:

1. **`MovableText`는 글자를 `scale.z`가 아니라 `2 × scale.z` 높이로 그린다.**
   `scale.z = 0.012`는 실제 24 mm이고, 줄 간격을 `0.012 × 1.25 = 15 mm`로 줬으니
   **줄이 9 mm씩 겹쳐** 뭉개졌다. 줄 간격 배수는 **2.0 이상**이어야 한다.
2. `liberation_sans.fontdef`에 `code_points`가 없어 아틀라스가 **33~166만** 담는다.
   한글은 물론 `°`(176)·`·`(183)도 글리프가 없고, 없는 글리프는 **예외도 경고도 없이**
   폭 1.0(정사각)에 넓이 0인 UV로 그려진다 — 안 보이는데 자리는 차지한다.

폰트 자체는 정상이다(`rviz2 --ogre-log` → `Ogre.log`에 `Liberation SansTexture`
512x256 생성 확인). **텍스트가 이상하면 폰트를 의심하기 전에 이 두 가지를 볼 것.**

### 함정 15 — ACM은 프로세스보다 오래 산다

ACM 완화를 켠 스윕을 `kill -9`로 죽이면 teardown이 안 돌고 **완화가 씬에 그대로
남는다.** 그 상태에서 완화 없이 돌린 다음 실행이 그걸 물려받아, **껐다고 믿으며
켠 상태로 재게 된다.** 실제로 겪었다 — "ACM off"인데 결과가 on과 똑같이 나왔다.

`verify_scene`은 토마토 개수와 octomap voxel만 보고 **ACM은 안 본다.** 그래서
`sweep_targets_planned.py`는 이제 `--octomap-acm` 유무와 무관하게 **항상**
ACM 상태를 명시적으로 맞춘다(끌 때도 호출).

같은 이유로 **조건을 결과에 반드시 같이 적을 것.** 조건이 다른 두 수치를 섞어
보고해 "#8이 500 → 722°로 우회한다"는 잘못된 결론을 낸 적이 있다 — 그 722°는
ACM을 켠 값이었고, 끈 상태에서 #8은 우회가 아니라 **도달 불가**였다.

`[시각화 제안]` **함정 15개를 경고 카드**로. `ROSBAG_HANDOFF.md`의 함정 카드와 같은
양식으로 만들면 두 문서가 한 세트로 읽힌다. 함정 3은 "같은 경로, 장애물 유무에 따라
288 vs 379" 대비도가 좋고, 함정 11은 **토마토 단면에 voxel을 겹쳐 그린 그림**이
좋다 — padding 0.5는 열매 자리가 비어 있고(구멍), 0.2는 열매 표면에 voxel이
붙어 있는 두 장 대비.

## 3. 현재 구현 상태

### 3.1 사이클 구조

```
look pose                     관측(스냅샷) — 시퀀스당 1회
   ↓
[0/5] armed pose              0.5초 정지. 이미 armed면 건너뜀
   ↓
[1/5] 정렬 → [2/5] 그리퍼 → [3/5] 접근 → [4/5] 파지 → [5/5] 후퇴
   ↓
armed pose 복귀               다음 토마토는 여기서 바로 [1/5]로
   ↓ (큐 소진 시)
look pose                     다음 관측 준비
```

### 3.2 변경된 파일

| 파일 | 변경 |
|---|---|
| `coord_to_goal_node.py` | `ARMED_POSE_JOINT_POSITIONS`, `_start_planning`에 `[0/5]` 경유 단계, 복귀 목표 교체, `_verify_approach_reference_point` 호출 위치 이동, `use_armed_pose` 파라미터 |
| `harvest_sequence_node.py` | 시퀀스 종료 시 `/go_to_look_pose` 호출 |
| `yolo_d435_detector_node.py` | **변경 없음** — 좌표 정합성이 이미 보장됨 |

**되돌리기**: `-p use_armed_pose:=false` (재빌드 불필요). 그러면 복귀가 look pose로
돌아가고 `[0/5]` 경유도 건너뛴다.

### 3.3 주의할 결합

- **`APPROACH_REFERENCE_POINT`는 그대로 둔다.** look pose flange 위치이고 접근 고도각
  프로파일의 기준이다. armed pose 도입으로 바뀌는 것은 계산이 아니라 의미론뿐이다
  ("보고 있는 자리에서 곧게 다가간다"가 더는 문자 그대로가 아님). 상수 검증
  (`_verify_approach_reference_point`)은 팔이 실제로 look pose에 있는 유일한 시점
  (`/go_to_look_pose` 완료)으로 옮겼다 — 안 옮기면 오탐 경고가 뜬다.
- **armed pose에서는 카메라가 베드를 안 본다.** YOLO 판단 게이팅이 안 열리는데,
  시퀀스 진행 중에는 오히려 안전하다(자동 재트리거 방지). 대신 **다음 스냅샷 전에
  반드시 look pose로 한 번 가야 한다** — `harvest_sequence_node`가 큐 소진 시 처리한다.

|---|---|---|
| 위치 | g_base `(0, 0.15, ·)` — 왼쪽 | 림 높이 스윕(반복 30회) |
| 림(입구) | z = **0.100** | 현재 0.150에서 50 mm 낮추면 이동량 −27% |
| 안쪽 바닥 | z = 0.050 | 내부 깊이 50 mm 유지 |
| 놓는 지점 | 그리퍼 끝단 z = **0.130** (림 위 3 cm) | 1 cm면 point 조건이 12회 중 5회 실패 |
| 목표 제약 | 위치 6×6 cm 상자 + **yaw 자유** | 아래 |

**두 자유도의 역할이 다르다** (통 형상 포함, y=0.15):

| 조건 | 성공률 | 이동량 |
|---|---|---|
| point (5 mm 구 + 방향 빡빡) | 79.2% | 440° |
| box (6×6 cm 상자) | 95.8% | 415° |
| **yaw 자유** | **100%** | 404° |
| box + yaw | 95.8% | **380°** |

`box`는 **도달 가능성**을 살리고, `yaw`는 **이동량**을 줄인다. 통이 없을 땐 네 조건이
다 100%라 이 차이가 안 보인다.

**수직 하강 방식은 기각했다.** `armed → 호버 → (Cartesian 수직) → 놓는 지점`은
직접 이동(316°)보다 62% 비싸고(513°) Cartesian이 자주 막힌다(호버 +10 cm에서 fraction
중앙값 0.59). 호버 지점이 놓는 지점보다 비싸서 하강분이 붙기 전에 이미 손해다.

`[시각화 제안]` **통 사양 단면도.** 림 0.100 / 바닥 0.050 / 놓는 지점 0.130을 치수선으로
그리고, 옆에 "box=도달성, yaw=이동량" 두 화살표를 다른 색으로. 아래에 조건별 성공률

## 5. octomap 재검증 — 줄기·지지대를 넣고 다시 쟀다

> 원래 "남은 일 1번"이던 항목이다. 4절까지의 모든 수치는 씬에 **열매(구)만**
> 넣고 잰 것이라 낙관적이고, 그게 실물과의 가장 큰 차이일 가능성이 높다고
> 적어 두었다. 그 형상은 이미 `bags/bed_look_slim`에 들어 있으므로 재생해서
> octomap으로 만들고, 그 위에서 다시 쟀다.

### 5.1 octomap을 파일로 떼어낸다

`scripts/octomap_io.py`. 재생 세션에서 만들어진 octomap을 `capture`로 파일에
굳히고, 가벼운 측정 스택에 `inject`로 되돌린다.

왜 굳히나 — octomap 한 번 만들려면 스택 + republish 2개 + 필터 2개 + YOLO +
bag 재생을 띄우고 워밍업까지 기다려야 한다. 측정은 그 뒤 수십 분씩 걸리고
여러 번 반복해야 한다. 그리고 더 중요한 이유가 있다:

> **octomap은 재생할 때마다 달라진다.** 실측으로 1분 사이에 982 → 988 voxel로
> 늘었다. 파일로 고정하지 않으면 "armed pose가 나아졌나"와 "octomap이 달라졌나"를
> 구분할 수 없다(함정 10과 같은 문제).

**부수적으로 얻은 것 — octomap을 파이썬으로 읽게 됐다.**
`sensors_3d.yaml`에 *"octomap 메시지가 표준 .ot/.bt 파일 헤더 형식이 아니라서
파이썬으로 직접 디코딩도 실패함"*이라는 기록이 있었는데, 관찰은 맞고 결론이
반만 맞았다 — **헤더가 없을 뿐 본문은 표준 octree 스트림**이다. `Octomap.binary`
플래그가 어느 형식인지 알려준다:

| 형식 | 노드당 | 내용 |
|---|---|---|
| full (`binary=False`) ← MoveIt이 주는 것 | **5바이트** | float32 log-odds + 자식 존재 비트 1바이트. 자식 비트 0이면 리프, 점유는 log-odds ≥ 0 |
| binary (`binary=True`) | 2바이트 | 자식 8개 × 2비트 |

실측 63350바이트 = 12670노드 × 5로 정확히 나누어떨어져 확인됐다. 이제
`octomap_io.py stats`로 **점유 voxel 개수·bbox·토마토별 주변 voxel 수**를
직접 셀 수 있다 — "바이트 수" 같은 간접 지표를 안 써도 된다.

### 5.2 octomap에 무엇이 들어 있나

`bags/bed_look_slim` 재생 + `/clear_octomap` 후 재형성. 해상도 20 mm.

| padding | voxel | 점유 부피 | 열매 5cm 이내 | 열매 10cm 이내 |
|---|---|---|---|---|
| **0.5 (현재값)** | 988 | 8128 cm³ | 12/15개, 합 92 | 15/15개, 합 881 |
| 0.2 | 1062 | 8776 cm³ | 15/15개, 합 273 | 15/15개, 합 1475 |

범위는 x +0.17~+0.97, y −0.33~+0.59, z −0.15~+0.47 (g_base).

**열매를 지운 클라우드에서 나온 것이므로 여기 들어 있는 것은 줄기·지지대·잎·베드다** —
정확히 지금까지 빠져 있던 것. padding 0.5에서도 **15개 토마토 전부가 10 cm 이내에
voxel을 가진다**(개당 17~106개). 즉 "줄기가 경로를 막는가"는 가정이 아니라 사실이다.

**단 0.2 쪽은 그대로 쓰면 안 된다 — 함정 11을 반드시 읽을 것.**

### 5.3 결과 — 씬 4종 × 시작 자세 2종

`scripts/eval_bed_scene.py`. **한 프로세스 안에서** 씬만 갈아 끼워 잰다(함정 10).
목표 15개 × 반복 30회 × 8조합, 방향 허용오차 0.2(노드와 같은 값), 총 870초.

이동량은 **목표별 최소의 중앙값**이다 — Phase 3(N개 중 최소 선택)이 적용된 상태를
가정한 값이고, 4절의 502°와 같은 집계다.

| 씬 | 시작 자세 | 성공률 | 도달 | 이동량 중앙 | 최악 |
|---|---|---|---|---|---|
| empty | look | 100% | 15/15 | 492° | 574° |
| empty | armed | 100% | 15/15 | 472° | 531° |
| tomato | look | 100% | 15/15 | 490° | 569° |
| tomato | armed | 100% | 15/15 | **406°** | 486° |
| octomap | look | 74.7% | 14/15 | 537° | 600° |
| octomap | armed | 77.8% | 14/15 | 505° | 659° |

| **full** | **armed** | **76.7%** | **14/15** | **478°** | 575° |

### 5.4 읽어야 할 것 넷

**1. armed pose 결정은 유지된다.** full 씬에서 armed 478° vs look 527° — **−9.3%**다.
열매만 있을 때의 −17%보다 줄었지만 방향은 같고, 최악값도 575 vs 597로 낫다.
**octomap을 넣었다고 armed pose를 재검토할 이유는 없다.**

**2. 진짜 대가는 이동량이 아니라 성공률이다.** 이게 이 절의 핵심이다.

> 이동량은 490 → 527° (+7.6%)로 완만한데, **성공률은 100% → 77.8%로 떨어진다.**
> 지금까지 이 작업은 "얼마나 빠른가"를 최적화해 왔는데, 줄기·지지대를 넣으면
> 병목이 **"갈 수 있는가"로 옮겨간다.**

플래닝 4번 중 1번이 실패한다는 뜻이고, 노드는 실패하면 재시도하므로 사이클
시간에 그대로 얹힌다. 이동량 −9%를 얻으려고 튜닝한 것보다 이쪽이 크다.

**3. 열매 구는 octomap 앞에서 거의 의미가 없다.** octomap 씬(열매 없음)과 full 씬
(열매 있음)의 차이가 505 → 478°, 537 → 527°로 **함정 10의 잡음 폭(±8%) 안**이다.
octomap이 이미 열매 주변을 채우고 있어서 구를 더 넣어도 새로 막히는 것이 별로 없다.

> 뒤집어 말하면 **4절의 "토마토 포함" 수치는 사실상 빈 씬에서 잰 것에 가깝다.**
> 진짜 장애물은 열매가 아니라 그 주변 구조물이었다.

**4. armed pose 자체는 octomap 안에서 안전하다.** 네 씬 모두에서 look → armed
플래닝이 성공했고 이동량이 48~50°로 일정했다. 1차 armed pose가 베드에 7.3 cm까지
파고들었던 사고(1.1절)를 생각하면 이건 반드시 확인해야 할 항목인데,
`eval_bed_scene.py`가 씬마다 자동으로 검사한다.

### 5.5 어떤 토마토가 막히는가 — 낮은 것부터

full 씬 / armed pose, 반복 30회. 성공 횟수를 높이순으로:

| 높이 z | 5cm내 voxel | 10cm내 voxel | 성공/30 |
|---|---|---|---|
| **0.161** | 9 | 71 | **4** |
| **0.169** | 8 | 59 | **0** |
| 0.217 | 6 | 66 | 23 |
| 0.224 | 4 | 51 | 27 |
| 0.261 | 14 | 82 | 26 |
| 0.265 | 0 | 17 | 30 |
| 0.346 | 18 | 106 | 16 |
| 0.361 | 9 | 87 | 24 |

**막히는 것은 가장 낮은 두 개다.** 그리고 상관을 보면 원인이 국소적이지 않다:

| | 성공 횟수와의 상관 |
|---|---|
| 높이 z | **+0.58** |
| 10cm 이내 voxel 수 | −0.36 |

즉 **"열매 주변에 줄기가 많아서"보다 "낮아서" 막힌다.** 낮은 열매는 팔이 아래로
들어가야 하는데, 그 아래가 베드 구조물이고 **팔뚝(joint2~4)에는 ACM 완화가
없다**(함정 4 — 의도적으로 그렇게 뒀다. 팔이 베드를 관통하는 경로는 걸러야 하니까).

> 이건 튜닝으로 풀 문제가 아닐 수 있다. 낮은 열매는 접근 고도각을 바꾸거나
> (위에서 내려다보기) 베이스를 옮기는 등 **기구학 밖의 답**이 필요할 수 있다.

### 5.6 이 수치의 유효 범위 — 반드시 같이 읽을 것

**(a) padding 값 하나가 답을 바꾼다.** 함정 11. 0.5는 줄기를 지워 낙관적이고,
0.2는 열매를 남겨 인공적으로 비관적이다(19.3%). 참값은 그 사이인데 **지금
도구로는 그 사이를 만들 수 없다.**

참고로 padding 0.2에서도 **armed pose의 상대 우위는 유지된다**(507 vs 556°, −8.8%,
도달 목표는 양쪽 다 같은 5개). 결론 1은 두 padding 양쪽에서 성립한다.

**(b) 노드는 플래닝 직전에 octomap을 지운다.** `coord_to_goal_node`의
`_continue_planning_from_armed`(L1677)가 매 목표마다 `/clear_octomap`을 부른다.
`max_update_rate`가 1.0 Hz이므로 정렬 플래닝이 도는 0.3~2초 동안 octomap은
거의 비어 있다. 게다가 armed pose에서는 카메라가 베드를 안 본다(3.3절).

> **즉 5절은 "octomap이 온전히 있을 때"를 쟀고, 실물은 "거의 비어 있을 때"로
> 돌고 있다.** 어느 쪽도 의도한 설계가 아니다 — 지금 실물은 장애물 회피가
> 사실상 꺼진 채 도는 셈이고, 켜면 성공률이 77%가 된다. 이 둘 중 무엇을
> 원하는지 결정해야 한다(6절 남은 일 1번).

**(c) 여전히 FakeSystem이고, 이 장면 하나다.** 토마토 15개짜리 실험실 베드
한 장면의 octomap이다. 다른 배치에서 같은 비율이 나온다는 근거는 없다.

`[시각화 제안]` 이 절에서 그림 셋.
(a) **성공률 막대 대비** — empty/tomato 100% vs octomap/full 77% vs padding0.2 19%.
    셋째 막대에 "측정 인공물" 경고 표시를 달아야 오독을 막는다.
(b) **높이 vs 성공 산점도** — x축 z(0.16~0.36), y축 성공/30. 낮은 두 점이 바닥에
    붙고 나머지는 위에 몰린 그림. 점 크기를 10cm내 voxel 수로 하면 "크기가 아니라
    위치가 결정한다"가 같이 보인다.
(c) **씬 4종 개념도** — 빈 씬 / 구만 / octomap만 / 둘 다. 위에서 본 단면으로
    무엇이 들어 있는지 대비.

### 6.1 씬별 도달성과 비용

> **이 표는 전부 `--octomap-acm` 없음(= 현재 배포 조건) 기준이다.** 완화를 켜면
> 6.3절 표대로 성격이 달라진다. 두 조건을 섞어 인용하지 말 것 — 실제로 한 번
> 섞어 보고해 "#8이 우회한다"는 잘못된 결론을 냈다(함정 15).

| 씬 | 시작 자세 | 성공률 | 도달 | 이동량 중앙 | 최악 | A/B 분기 |
|---|---|---|---|---|---|---|
| 열매만 | look | 100% | 15/15 | 415° | — | 13/2 |
| 열매만 | armed | 100% | 15/15 | **358°** | — | 13/2 |
| 열매+octomap | look | 65.1% | 13/15 | 421° | 551° | 12/1 |
| 열매+octomap | armed | 70.2% | 13/15 | **357°** | 519° | 12/1 |
| 열매+octomap+벽 | look | 66.2% | 13/15 | 406° | 554° | 12/1 |
| **열매+octomap+벽** | **armed** | **68.9%** | **13/15** | **373°** | 530° | **12/1** |

읽어야 할 것 넷.

**1. armed pose의 우위가 커졌다.** full 씬에서 373 vs 406°(−8%)이고, 열매만 있는
씬에서는 358 vs 415°(−14%)다. 5.3절(−9.3%)과 같은 방향이다.

**2. 벽은 측정 가능한 영향이 없다.** 벽 유무로 65.1↔66.2%, 357↔373° —
전부 세션 잡음 폭(±8%, 함정 10) 안이다. 벽이 팔의 작업 영역 밖에 있다는 뜻이고,
**등록해 두는 값어치는 "영향이 없음을 확인했다"는 것**이다.

다만 **여유가 크지 않다.** `/check_state_validity`로 잰 경계:

| 벽 y | 높이 | look pose | armed pose |
|---|---|---|---|
| −0.20 | 150 mm | OK | **OK** (현재값) |
| −0.18 | 150 mm | OK | 충돌(joint5) |
| −0.20 | **180 mm** | OK | 충돌(joint5) |
| −0.22 | 180 mm | OK | OK |

즉 **20 mm만 안쪽으로 와도, 또는 30 mm만 높아져도 armed pose가 깨진다.**

> **이때 "충돌하지 않는 다른 경로"는 없다.** armed pose는 경로가 아니라
> **고정된 관절 자세 하나**다. 그 자세 자체가 충돌이면 어떤 경로로도 갈 수 없다.
> 선택지는 (a) 벽을 물리거나 (b) 낮추거나 (c) **다른 armed pose를 쓰는 것**뿐이다.

(c)를 수치로: 벽 −0.18 / 180 mm에서 armed pose의 J1을 훑으면
**J1 ≤ +20°만 유효**하고 +30°부터 joint5가, +50°부터 joint4까지 걸린다.
현재 armed pose는 J1 **+40°**다. 즉 그 벽이 실측이라면 armed pose를 +20° 이하로
낮춰야 하고, 그만큼 이득(J1을 목표 쪽으로 미리 돌려두는 것)이 줄어든다.

**3. B분기가 거의 사라졌다.** 12/1 — 5.3절에서 8/5~13/2이던 것이 한 개로 줄었다.
`WORLD_UP` 수정의 부수 효과다(6.2절).

**4. 이동량이 5절보다 크게 낮다.** 5.3절 full/armed 478° → 지금 357°(−25%).
씬 정의는 같고 코드만 바뀌었으므로 `WORLD_UP` 수정의 효과로 본다.

### 6.2 그리퍼 자전(J6) — 이번 수정의 핵심

RViz 관찰: *"목표로 진입할 때 flange가 축을 기준 180도 회전한다"*.

원인은 **roll 기준 벡터가 뒤집혀 있던 것**이었다. `_compute_look_at_quat_xyzw`가
roll 0을 `WORLD_UP`(월드 +Z) 기준으로 정하는데, look pose flange의 실제
orientation과 비교하니 **−177.9도** 차이였다. 즉 `roll=0`이 곧 뒤집힌 자세였고,
roll 후보 탐색이 IK 실패로 전멸하면 빠지는 `roll 0` 강행 폴백이 하필 그쪽이었다.

`WORLD_UP`을 −Z로 바꾼 결과:

| | 수정 전 | 수정 후 |
|---|---|---|
| look pose와 roll 0의 편차 | 177.9° | **2.1°** |
| 목표 15개의 roll 0 편차 | 157~177° | **3~23°** |
| J6 자전량(실측, 반복 6) | 중앙 166° | **13/15가 0~25°** |

**예외 2개.** #3(z=0.224)은 roll 0/30/60에서 IK가 안 풀리고 90~300°에서 풀린다 —
노드는 roll 후보 12개를 훑으므로 찾아내지만, **스윕 스크립트는 roll 0만 시도해
"도달 불가"로 잡는다**(함정 5의 또 다른 얼굴). #15(z=0.161)는 뒤집힌 orientation이
유일한 해라 J6가 167° 돈다 — 그 목표는 어차피 6.4절의 문제아다.

> **이 상수는 look pose와 결합돼 있다.** look pose를 바꾸면 부호가 맞는지 다시
> 재야 한다. 어긋나도 **에러가 안 나고 그리퍼만 뒤집힌 채 정상 동작**한다.

### 6.3 직진 접근([3/5])의 Cartesian 성공률 — 새로 드러난 병목

지금까지 스윕은 **[1/5] 정렬만** 재고 있었다. `--straight-in`으로 정렬 자세에서
flange 목표까지의 직진 구간을 노드와 같은 서비스·같은 해상도로 재 봤다
(standoff 30 mm, 반복 4회).

| 씬 | fraction ≥ 0.95 |
|---|---|
| 열매만 | **14/15** (대부분 100%) |
| 열매 + octomap + 벽 | **4/13** |

**직진을 막는 것은 열매도 standoff도 아니고 octomap이다.** 열매만 있으면 거의
전부 100%인데 줄기 voxel이 들어가면 3분의 1로 떨어진다.

노드의 사전 dry-run(`_verify_grasp_approach_reachable`)이 `CARTESIAN_FRACTION_THRESHOLD
= 0.95`로 거르므로, **이 상태라면 대부분의 목표가 정렬 재시도(최대 5회)로 간다.**
5절이 "성공률이 병목"이라고 했는데, 그 병목의 상당 부분이 정렬이 아니라 **여기**다.

standoff 자체는 무죄다 — 20 mm에서 3/12, 30 mm에서 4/13으로 차이가 없다.

#### 그런데 이건 물리적 한계가 아니라 **ACM 설정 구멍이었다**

함정 4에서 토마토(구)에 걸어 준 완화를 **octomap에는 안 걸고 있었다.**
"octomap은 줄기·지지대라 그리퍼가 스쳐도 되는 대상이 아니다"라고 5절에 적어
두었는데, 그 판단의 대가를 재 보지 않았던 것이다. 같은 10개 링크
(그리퍼 6 + 손목 2 + flange)에 대해서만 `<octomap>` 충돌을 허용하고 다시 쟀다
(`scene_objects.allow_gripper_octomap_collisions`):

| | 정렬 성공률 | 도달 | 직진 ≥0.95 | 직진 중앙 |
|---|---|---|---|---|
| 완화 없음(현재) | 70.0% | 13/15 | 3/13 | 0.25 |
| **그리퍼/손목만 완화** | **100%** | **15/15** | **14/15** | **1.00** |

**octomap이 없을 때의 기준선으로 완전히 복귀한다.** 5절이 "성공률 100% → 77%"를
줄기·지지대의 물리적 대가로 읽었는데, 그 대부분이 실은 **완화를 안 건 탓**이었다.

**팔뚝(joint2~4)은 그대로 금지다** — 팔이 베드나 지지대를 관통하는 경로는 여전히
걸러진다. 바뀌는 것은 "손가락·손목이 잎이나 줄기를 스쳐도 되는가"뿐이다.

> **다만 이건 판단이 필요한 완화다.** octomap voxel은 **잎과 지지대를 구분하지
> 못한다.** 잎을 스치는 것은 괜찮아도 금속 지지대를 미는 것은 곤란하다.
> 그래서 이 절은 "이렇게 하면 된다"가 아니라 **"대가가 이만큼이다"**로 읽을 것.
> 적용 여부는 7절 남은 일 2번의 결정에 딸려 있다.

**단, 5.6(b)를 같이 읽을 것.** 노드는 플래닝 직전에 `/clear_octomap`을 부르므로
실물에서는 이 dry-run이 거의 빈 octomap을 본다. 즉 **여기 수치는 "장애물 회피를
켰을 때"이고, 지금 실물은 "꺼진 채" 돈다.**

### 6.4 접근 기하 (standoff 30 mm)

| 항목 | 값 | 20 mm 대비 |
|---|---|---|
| 기하 게이트 통과 | 15/15 | 동일 |
| 채택 고도각 | **−10 ~ +15°** | **완전히 동일** |
| \|고도각\| 평균 | 8.7° | 동일 |
| 수직 우회 평균 | 18 mm | 17 mm |
| 정렬 반경 | 0.130~0.175 m | 0.140~0.184 |

**30 mm는 접근 방향을 하나도 안 바꾸면서 직진 구간만 1.5배로 늘린다.**
40 mm부터 고도각이 기울고 50 mm에서는 −35~+30°/우회 47 mm로 튄다
(`APPROACH_STANDOFF_M` 주석의 표 참고). *"목표 50 mm 앞에서 직진"* 요구는
**게이트를 0.11로 낮추지 않는 한 성립하지 않으며**, 낮추면 필요 J1이
34° → 41°로 늘어 2026-07-30 리팩터가 없앤 베이스 스윙이 일부 돌아온다.

#8은 5.5절에서 이미 나온 "가장 낮은 열매" 문제와 같은 건이다. 높이와 성공의

`[시각화 제안]`

(b) **직진 fraction 대비** — "열매만 14/15" vs "octomap 포함 4/13" 막대 두 개.
    0.95 게이트선을 수평 점선으로 그으면 병목이 한눈에 보인다.
(c) **standoff vs 고도각** — x축 standoff(20~50mm), y축 |고도각| 평균(8.7→20°)과
    수직 우회(17→47mm)를 이중축으로. 30mm까지 평평하다가 40mm부터 꺾이는 모양.

#### 1) 측정 스택 띄우기 (터미널 A)

로봇도 카메라도 필요 없다. **필터 노드까지 꺼야 한다** — 클라우드 발행자가
살아 있으면 주입한 octomap을 occupancy_map_monitor가 덮어쓴다.

```bash
ros2 launch mycobot_280_moveit2 demo_octomap.launch.py \
    enable_octomap:=false enable_camera:=false \
    enable_pointcloud_filter:=false use_rviz:=false
```

30초쯤 뒤 다른 터미널에서:

```bash
pgrep -xc move_group          # **반드시 1** (함정 1)
```

> `enable_octomap:=false`인데도 `ros2 param get /move_group sensors`가
> `['d435_pointcloud']`로 나온다 — 알려진 버그다(함정 2). 클라우드 발행자가
> 없으므로 실질 영향은 없다.

#### 2) RViz 띄우기 (터미널 B)

```bash
rviz2 -d src/mycobot_280_pick/config/sweep_view.rviz
```

보이는 것: 팔(RobotModel), **재생(RobotState, `/sweep_robot_state`)**,
장애물(PlanningScene — octomap voxel + 토마토 구), 토마토 마커와 상태 라벨.

> `Trajectory` 디스플레이는 **꺼져 있는 것이 정상**이다. 재생은 스크립트가
> 직접 그린다(함정 14 옆의 설명). 켜면 두 벌이 겹쳐 재생된다.

#### 3) 스윕 돌리기 (터미널 C)

**가장 실물에 가까운 조합** — 열매 + 녹화 octomap + 벽, armed pose 출발,
정렬에 이어 [3/5] 직진까지 재생:

```bash
python3 -u scripts/sweep_targets_planned.py \
    --repeat 5 --orientation-tolerance 0.2 \
    --tomatoes --octomap bags/bed_look_octomap_wall.bin \
    --start-pose 40 104.06 -56.68 -50 15.99 1.4 \
    --straight-in \
    --display-pause 1.0 --display-seconds 6 --display-repeats 3 --display-loop 0
```

| 옵션 | 뜻 |
|---|---|
| `--tomatoes` | 열매 15개를 구로 넣고 ACM을 푼다(함정 4) |
| `--octomap FILE` | 녹화 장면 octomap 주입 |
| `--octomap-acm` | **여기 없다.** 붙이면 그리퍼가 줄기 voxel을 스쳐도 되게 한다(6.3절). 붙인 값과 안 붙인 값을 **섞어 보고하지 말 것** |
| `--start-pose` | armed pose. 빼면 look pose에서 출발 |
| `--straight-in` | [3/5] 직진 접근까지 계획해 이어 재생하고 fraction을 찍는다 |
| `--display-seconds 6` | 재생 1회 6초. **크게 줄수록 느리다** |
| `--display-repeats 3` | 목표당 3회 반복 |
| `--display-loop 0` | Ctrl+C까지 무한 반복 |

터미널에 목표마다 한 줄씩 나온다:

```
ripe     z=0.338  성공 5/5  J1 47~158°  J6 4°  이동량 549°±113  플래닝 0.07s  직진 93%
```

`J6`가 flange 자전량(뒤집힘 지표, 6.2절), `직진 %`가 Cartesian fraction(6.3절)이다.

#### 4) 화면 읽는 법

좌측 라벨(베드 옆구리, 4줄):

```
armed_pose
#4/15:ripe:z0.22
trv534:J1+127
J6:11:B-wrap:3/5
```

색: **파랑=A분기**(목표를 향해 곧게), **주황=B분기**(뒤로 감김, 비쌈),
**빨강=도달 불가**. 라벨에서 현재 목표까지 지시선이 이어진다.

> **라벨에 공백을 넣지 말 것.** 스페이스는 폰트 아틀라스에 없어서 하나당
> 50 mm 간격이 된다(함정 14). 크기·위치는 `--label-scale`, `--label-pos`로 조정.

#### 5) 수치만 필요할 때 (화면 없이)

씬 구성을 교차 비교하려면 이쪽이 낫다 — 한 프로세스 안에서 씬만 갈아 끼우므로
세션 차이가 안 섞인다(함정 10):

```bash
python3 -u scripts/eval_bed_scene.py --repeat 30 \
    --scenes tomato full --poses look armed \
    --octomap bags/bed_look_octomap_wall.bin \
    --csv bags/my_eval.csv
```

standoff나 roll을 A/B 하려면 스윕 쪽 인자를 쓴다:

```bash
python3 -u scripts/sweep_targets_planned.py --repeat 10 --orientation-tolerance 0.2 \
    --tomatoes --octomap bags/bed_look_octomap.bin \
    --start-pose 40 104.06 -56.68 -50 15.99 1.4 \
    --standoff 0.02          # 노드 상수 대신 이 값으로
```

#### 6) octomap을 새로 만들 때 (5.1절)

**이때만 재생 스택을 쓴다.** 측정 스택과 **같이 띄우면 안 된다**(함정 1).

```bash
# 6-1) 측정 스택을 완전히 내린 뒤 재생 스택
ros2 launch mycobot_280_pick scene_replay.launch.py use_rviz:=false bbox_padding:=0.5

# 6-2) 로그에 "Octomap cleared."가 찍히고 40초쯤 더 기다린 뒤
python3 -u scripts/octomap_io.py stats                      # voxel 개수 확인
python3 -u scripts/octomap_io.py capture --out bags/bed_look_octomap.bin

# 6-3) 벽을 합치려면
python3 -u scripts/octomap_io.py add-box \
    bags/bed_look_octomap.bin bags/bed_look_octomap_wall.bin --wall

# 6-4) 재생 스택을 완전히 내리고 1)로 돌아가 측정 스택으로 갈아탄다
```

`bbox_padding`을 낮추기 전에 **함정 11을 반드시 읽을 것** — 0.2로 낮추면
열매가 octomap에 들어와 측정이 망가진다.

#### 7) 되돌리기

노드 동작을 원래대로 보려면 재빌드 없이:

```bash
ros2 run mycobot_280_pick coord_to_goal_node --ros-args -p use_armed_pose:=false
```

#### 측정 전 체크리스트 (함정 요약)

- [ ] `pgrep -xc move_group` = **1** (함정 1)
- [ ] `--orientation-tolerance 0.2` — 노드와 같은 값 (함정 5)
- [ ] 반복 **30회** 이상 — 10회로는 도달 가능성 판정이 뒤집힌다 (함정 6·9)
- [ ] 씬이 의도한 상태인지 로그의 `씬 확인:` 줄 확인 (함정 8)
- [ ] 조건 비교는 **한 세션 안에서** — 세션이 다르면 ±8% 흔들린다 (함정 10)
- [ ] `--octomap-acm`을 켰는지 껐는지 **결과에 같이 적을 것** (6.3절)
- [ ] 통과 수뿐 아니라 **채택된 값**(고도각 등)도 볼 것 (함정 12)
