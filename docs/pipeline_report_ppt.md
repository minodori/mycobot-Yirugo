## 페이지 1. 왜 MoveIt2가 필요한가

### 검토한 선택지

1. **제조사 API(자체 솔버) 직접 사용** — `pymycobot`으로 좌표→관절각 IK를 바로 호출
   - 지금처럼 **제한된 토마토 베드** 환경(작업 반경 좁음, 장애물 패턴 단순)에서는 이 방식으로도 큰 문제 없이 동작 가능
2. **자체 경로 계획 솔버 개발** — 필요하면 충돌 회피/경로 최적화를 직접 구현
   - 유연성은 최대지만 **복잡도가 높아** 짧은 개발 기간 안에 완성해서 적용하기 어려움

### 채택: 이미 검증된 오픈소스 플랫폼(MoveIt2) 사용

- MoveIt2는 **솔버(OMPL) 하나만을 지칭하지 않음** — 아래를 포함한 통합 로보틱스 플랫폼
  - **OMPL**: 경로 계획(motion planning) 솔버
  - **TF2**: 카메라 좌표 ↔ 로봇 베이스 좌표 등 좌표계 변환
  - **충돌 예측**: Octomap 기반 실시간 장애물 회피
  - **캘리브레이션**: `easy_handeye2` 등 핸드-아이 캘리브레이션 연동
- **RViz 연동**: 카메라 영상, 포인트클라우드, 계획 경로, TF 트리 등 모든 토픽을 실시간 시각화
  - 개발/디버깅 중 "지금 로봇이 무엇을 보고 왜 이렇게 계획했는지"를 눈으로 바로 확인 가능 → 검증 속도 향상

**[이미지: MoveIt2 구성요소 다이어그램 또는 RViz 실행 화면 캡처(로봇 모델+Octomap+계획 경로가 함께 보이는 장면)]**

## 페이지 2. 기술 파이프라인과 현재 진행 상황

### 파이프라인 흐름

```
D435 카메라 → YOLO 검출 → 3D 좌표 변환(TF2+handeye) → coord_to_goal_node
   → MoveIt2(OMPL) 경로계획 → ros2_control → sync_plan(RPi) → 실물 로봇
```

**[이미지: 위 파이프라인을 노드/토픽 박스 다이어그램으로 재구성 — `docs/Moveit2 setup record.md` 7장 구성도 참고]**

### 단계별 진행 현황

| 단계 | 내용 | 상태 |
| --- | --- | --- |
| 1. 검출 | D435 + YOLO, look pose 도달 시 2초 누적→클러스터링 후 1회 판단 | ✅ 완료(실물 검증) |
| 2. 좌표 계산 | 핸드-아이 캘리브레이션 기반 TF 변환 + depth 반지름 보정 | ✅ 완료(실물 검증) |
| 3. 목표 안전장치 | 반지름/방위각 범위 검증, 속도·가속 스케일링 | ✅ 완료(실물 검증) |
| 4. 장애물 회피 | Octomap + 포인트클라우드 사전 필터링 + MoveIt2 경로계획 | ✅ 완료(실물 검증, 일부 잔여 이슈 아래 참고) |
| 5. 실물 이동 | 정렬 → 목표 근접 위치까지 접근 → look pose 자동 복귀 | ✅ 완료(실물 검증) |
| 6. 다중 대상 처리 | `harvest_sequence_node`로 깊이순 큐잉 → 순차 접근 | ✅ 완료(실물 검증) |
| 7. 운영 편의 | RViz 우클릭 제어판, `/go_to_look_pose`, `/emergency_stop` | ✅ 완료(실물 검증) |
| 8. **그리퍼 파지(actuation)** | 정렬→그리퍼 열기→직진 접근→파지→후퇴 | 🔶 진행 중 — 정렬/그리퍼 열기까지 실물 확인, **직진 접근 단계 IK/OMPL reachability 문제로 막힘(다음 세션 최우선)** |

### 최종 아웃풋

**[이미지: 실물 로봇이 토마토를 검출해 접근 자세까지 도달한 장면 캡처 — 가능하면 RViz 화면(Octomap+계획 경로)과 실물 사진을 나란히 배치]**

### 남은 과제 (요약)

- 그리퍼 실제 파지 완성 (최우선)
- 파지 성공 여부 판정 로직
- Octomap 그리퍼 근접거리 self-filter 잔여 voxel로 인한 간헐적 충돌 판정 → 재평가 필요
- look→캡처→수확→복귀 완전 자동 반복 오케스트레이션
- `automato_ws`(팀 저장소)로 포팅

## 검토 의견 (2장 구성 외 참고용)

- **페이지 2 분량 주의**: 표에 8단계가 다 들어가면 슬라이드가 빽빽해질 수 있음. 1~7단계는 "완료" 한 줄로 압축하고, 8단계(그리퍼 파지)에 화면 공간을 더 주는 편이 "지금 어디 막혀있는지"를 더 명확히 전달함 — 청중이 궁금해할 지점이 바로 여기일 가능성이 높음.
- **최종 아웃풋 이미지**: 그리퍼 파지가 미완성이라 "완전한 수확 성공" 장면은 아직 없음. 발표에서 이 점을 숨기기보다, "여기까지 검증됨(접근) / 여기가 다음 목표(파지)"로 명시하는 게 신뢰도 면에서 나을 것 같음.
- **페이지 1 보강 옵션**: "왜 필요한가"에 자체 API 대비 MoveIt2의 실제 이득(예: 장애물 회피 없이 자체 API만 썼다면 지금 겪는 어떤 문제를 못 풀었을지)을 한 줄 추가하면 설득력이 더 붙을 것 같음. 원한다면 이 부분 문구도 다듬어줄 수 있음.
- 발표 시간이 짧다면 8단계 표 대신 "1~7단계 완료 / 8단계 진행중"으로 요약 문장 하나 + 표는 부록으로 빼는 것도 고려해볼 만함.
